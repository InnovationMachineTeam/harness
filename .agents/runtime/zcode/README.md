# ZCode adapter

There is no ZCode configuration file in this repository, and this README is the adapter in its place. The harness has no project-level hook - nothing it reads can install a PreToolUse matcher - so `config.json` beside this file declares `guard.hooksSupport: "behavioral"`. The guard is a command the agent must choose to run rather than a gate the harness applies:

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /"}}' | bun run guard --format=exit
```

A non-zero exit means the repository policy in `tooling/agentos/agent-hooks/src/policy.ts` blocks the call. The policy has one implementation; only the way a harness reaches it differs. ZCode does prompt for its own read and write permissions and runs shell in a sandbox, which is a second layer, not a replacement: the sandbox knows nothing about this repository's protected paths.

The model tiers in `config.json` are carried over from the donor system and are all marked `verified: false`. `bun run agents launch --runtime zcode` prints them with that flag showing, and the master confirms the mapping with the user before working. When ZCode gains a project configuration file, add it, point `vendorAdapter` at it, and rewrite `guard.notes`.

## What behavioural costs the session

Because nothing here can refuse a call, `agents launch --runtime zcode` caps the session mode at `semi-automatic` whatever `agent.json` declares, and says so in the launch output rather than leaving the reader to infer it from `hooksSupport`. For the same reason `delivery run --yes` refuses in this runtime unless `--gate-by <person>` names who approved: `--yes` writes the approval itself, and `$USER` is not an approver where the guard is a paragraph. `docs/platform/agent-runtime-configs.md` has the ladder and the third case, `MODE-UNENFORCED`.

## Reaching the console

This harness has no hook the repository can install, so the Harness Console cannot see what it does unless the agent tells it. One command does that, and it is the same command `.claude/settings.json` runs at a hook point - one emitter, one event stream, whatever ran (ADR-0019):

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"…"}}' | \
  bun tooling/agentos/console/bin/agentos-emit.ts tool.pre --source zcode
```

It exits 0 on every path and holds itself to 200 ms, so it can never fail the work it observes. Call it at the start of a session (`session.start`), before a tool call worth recording (`tool.pre`), and at the end (`session.end`). A session that emits nothing is a session the console reports as not having happened - `bun run agentos wrappers` says which harnesses are wired and how.

## The rules

The deny list below is generated from `tooling/agentos/agent-hooks/src/policy.ts`, the one implementation every harness obeys; `bun run guard docs --check` runs in `verify-fast` and fails when this document and the engine disagree. Do not edit inside the markers - change the policy and its tests instead. `bun run guard --explain <ruleId>` prints one rule in full.

The role a session runs as writes inside its own set (`.agents/write-sets.json`). With `AGENT_ROLE` set, a write outside that role's set is blocked rather than warned.

### Blocked

- `deploy.prod-apply` - **block** (deploy). Applying to a protected environment outside a release step. Instead: bun run delivery run <MID> <SID> - the deploy workflow holds the approval gate.
- `deploy.destructive` - **block** (deploy). Tearing down a deployed environment or a managed resource. Instead: Ask the user; a teardown is an always-gate in every autonomy mode.
- `shell.rm-rf-root` - **block** (shell). Recursive delete of an absolute, home or wildcard path. Instead: Name a repository-relative path, or ask the user to run it themselves.
- `shell.rm-rf-worktree` - **block** (shell). Deleting a worktree under .agents/.worktrees/ with rm leaves git's registration behind. Instead: bun run worktree:remove <slug> - it unregisters the worktree and its branch.
- `shell.rm-rf-outside-allowlist` - **block** (shell). Recursive delete outside the allowlist (.agents/.tmp, /tmp, .nx, node_modules). Instead: Delete the specific files, or do the work under .agents/.tmp/ instead.
- `shell.git-force-push` - **block** (shell). Force push discards published history. Instead: git push --force-with-lease, and ask the user first.
- `shell.history-rewrite` - **block** (shell). Repository-wide history rewrite. Instead: Ask the user; a rewrite invalidates every clone.
- `shell.chmod-777` - **block** (shell). chmod -R 777 makes the tree world-writable. Instead: Set the narrowest mode the failing step actually needs.
- `db.drop` - **block** (shell). Destructive database operation. Instead: Write a migration; the schema is generated from packages/core/data.
- `db.delete-without-where` - **block** (shell). DELETE without a WHERE clause. Instead: Add the predicate, or run it as a reviewed migration.
- `prisma.reset` - **block** (shell). Prisma reset drops the development database. Instead: bunx prisma migrate dev, which keeps the data.
- `gate.answer-by-agent` - **block** (gate). A gate is answered by a person; an agent writing its answer or calling gate:answer approves its own request. Instead: Tell the user the gate id and what it approves, and wait: they answer it in the console Inbox.
- `approval.by-agent` - **block** (gate). An approval is given by a person; an agent writing agent-change/approval.md, or running `agents approve`, approves its own change. Instead: Show the user the authority diff and the patches and ask them to run `bun run agents approve <run>` in a terminal: it opens a page, and its button writes the file.
- `secrets.read` - **block** (shell). Reading a secret file into the transcript. Instead: Read .env.example instead, or ask the user for the value you need.
- `net.pipe-to-shell` - **block** (shell). Executing a downloaded script without review. Instead: Download to a file, read it, then run it.
- `infra.production` - **block** (shell). Production or destructive infrastructure operation. Instead: Run it through the deploy workflow, which holds a gate before apply.
- `secrets.read-tool` - **block** (read). Read, Grep or Glob over a secret path puts its contents in the transcript. Instead: Read .env.example, or ask the user for the single value you need.
- `write.secret-path` - **block** (write). Writing a secret file would commit a credential or overwrite a live one. Instead: Change .env.example and tell the user which value to set.
- `write.protected-path` - **block** (write). Writing inside .git/, node_modules/ or bun.lock edits state a tool owns. Instead: Change the source the tool reads, then re-run the tool.
- `structural.guard-mutation` - **block** (structural). The guard source, the write-set register and the role charters decide what every agent may do; the author of such a change must not be its only approver. Instead: Show the user the exact change and why, and ask them to make it or approve it themselves; do not work around this block.

### Warned

- `deploy.billable` - **warn** (deploy). Creating a cloud resource costs money from the moment it exists. Instead: Confirm the cost with the user before the second step of the call.
- `shell.git-hard-reset` - **warn** (shell). Hard reset discards uncommitted work. Instead: git stash, or commit on a scratch branch first.
- `shell.git-clean` - **warn** (shell). git clean -fd deletes untracked files irreversibly, including active worktrees. Instead: git clean -nd first, and check git worktree list.
- `shell.sudo` - **warn** (shell). Elevated privileges requested. Instead: Prefer a user-scoped install; ask before changing the machine.
- `write.outside-set` - **warn** (write). The path is outside the write set of the role this session runs as; two writers over one path is the conflict the topology exists to prevent. Instead: Return the work to the master as a new task for the role that owns the path.
- `structural.agents-mutation` - **warn** (structural). A change under .agents/roles, skills, runtime or agents is a structural change to the agent system. Instead: Bring it to the user as a proposal: evidence, the change, the risks.

Recursive deletes are allowed only under `.agents/.tmp`, `/tmp`, `.nx`, `node_modules`; a worktree under `.agents/.worktrees/` is removed with `bun run worktree:remove <slug>`, never with `rm`.

Check a single action against the engine rather than against this list:

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"…"}}' | bun run guard --format=json
```

### After an edit

After writing a file, format, lint and type-check it before the next edit. Claude Code runs this as its `PostToolUse` hook; a harness without one runs it by hand:

```bash
bun run guard post-edit --format=cursor <path>…
```

It prints nothing when the file is clean. Otherwise each line names the file, the line, the rule and the tool. Fix what it reports unless the next edit in the same change resolves it; `verify-fast` refuses what is left.
