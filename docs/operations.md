# Эксплуатация: процессы, промпты, настройки, папки

## Процессы

Вкладка "Процессы" пространства рантайма: `ps axo pid,ppid,etime,pcpu,pmem,command`, отфильтрованный паттерном адаптера; тип `app` (путь содержит `.app/`) или `cli`.

Действия (`POST /api/processes/action`):

- **стоп** - SIGTERM → до 3 с грации → SIGKILL. Перед сигналом PID перепроверяется свежим срезом ps (защита от переиспользованных PID);
- **рестарт** - только для `app`: остановка + `open -a <ИмяПриложения>`. CLI-процессы перезапускать нельзя - их запускает пользователь.

## Промпты и "Исправить"

`POST /api/prompts/run {prompt | issue}` запускает промт в **новой** headless-сессии рантайма; процесс отвязанный (detached), вывод - в `.agents/console/runs/<ts>-<runtime>.log` (каталог в .gitignore), сессия появляется в общем списке.

Какой рантайм исполняет:

```
явный runtime в запросе → settings.taskRuntimes.promptExecution → defaultRuntime (★)
```

Значением задачи может быть провайдер реестра (`provider:<id>`, вкладка "Провайдеры"): тогда промт уходит в API провайдера в процессе консоли, ответ - в `.agents/console/runs/<ts>-provider-<id>.log` ([providers.md](providers.md)).

Кнопка **"Исправить"** во вкладке "Диагностика" формирует промпт по проблеме (`core/prompts.ts#buildFixPrompt`: заголовок, детали, рекомендация + требования соблюдать AGENTS.md/guard) и идёт через этот же роут. Если эффективный исполнитель не выбран - кнопка заблокирована с подсказкой.

Безопасность: промт санитизируется (NUL, длина 32 КБ, ведущий `-`); спавн - литеральные команды и массивы аргументов, без оболочки; логи - в игнорируемом каталоге.

Slash-команды композера "Агент" (`/master:<id>`, `/agent:<id>`, `/workflow:<id>`, `@путь`) раскрываются на сервере до запуска: навыки и роли - блоками в промте или системном промте провайдера, файлы - содержимым; `/workflow:<id>` запускает прогон workflow из direct-режима ([skills.md](skills.md)). Ошибка раскрытия (навык не найден, нет привязки, выключен тогглом) - HTTP 400, сообщение показывается в диалоге.

## Настройки: исполнитель под задачу

Страница "Настройки - Основные" собирает все кейсы использования провайдеров: задачи "Исполнение команд" и "Создание навыка" (рантайм, провайдер из реестра или "По умолчанию" = ★) и инструменты памяти "OpenWiki (сборка вики)" и "Graphify (сборка графа)" (провайдер реестра или "Вручную"). Рантайм - только известный harness; провайдер - только с заполненными полями и успешной проверкой; для инструментов - только с маппингом на пресеты инструмента. Хранится в `state.settings.taskRuntimes` (null = "по умолчанию", провайдер - `provider:<id>`) и в `openwikiLlm`/`graphifyLlm` (с `providerId`); клиентский стор обновляется после записи файла. Выбор провайдера для инструмента выводит поля пресета/ключа из его записи на сервере ([providers.md](providers.md)).

## Мониторинг: задачи

`/monitoring` - глобальная вкладка "Мониторинг" с внутренними вкладками **"Задачи"** и **"Статистика"**. Задачи (`core/tasks.ts`, `GET /api/monitoring/tasks`): в реестре видны все запуски консоли - промты в headless-сессиях рантаймов, запросы провайдерам (`provider:<id>`, in-process) и сборки OpenWiki/Graphify. Задачи независимы и выполняются **параллельно** - глобальных блокировок нет, блокировка только повторный запуск той же сборки в той же папке (409).

Строка задачи: заголовок (тема промта или режим и папка сборки), бейджи статуса (выполняется/завершена/ошибка/прервана), исполнителя (рантайм, провайдер или инструмент) и модели, ссылка на сессию (`/runtime/<id>?tab=sessions`) или раздел инструмента. По умолчанию показаны активные; фильтр - "Активные / Все / Завершённые"; при пустом списке - "Активных задач нет".

Механика: каждая задача пишет мету в `.agents/console/tasks/<id>.json` (pid, лог, смещение старта); статус `running` финализируется при чтении списка - процесс закончился или в логе с момента старта есть ошибка. In-process задачи провайдеров финализируют мету сами; после рестарта сервера зависшие помечаются `interrupted` (через 15 мин). Меты старше 30 дней удаляются.

Вкладка **"Статистика"** (`GET /api/stats`): таблицы workflow-запусков (runs, attempts и токены, роли, модели и стоимость) активного workspace, подписка и блок AgentPlane - версия CLI, признак инициализации workspace, число задач по статусам (TODO, DOING, BLOCKED, DONE; из `agentplane task list --all`). Стоимость показывается только при известной price card; подписка не распределяется по задачам.

## Рабочие папки

Вкладка "Рабочие папки" в Настройках (`/settings?tab=workspaces`): ровно одна **обязательная** папка (по умолчанию - корень репозитория; заменить можно, удалить - нет) + дополнительные - по умолчанию `docs/` и `sources/`. Валидация: абсолютный путь, существует, без дублей. Назначение - фильтрация сессий ([sessions.md](sessions.md)) и масштаб repo-сигналов активности.

Режимы записи: обязательная папка - всегда write mode, дополнительные - read mode. Хуки навыков (симлинки и команды манифеста) работают только с обязательной папкой; workflow-прогон в дополнительной папке исполняет write-ресурсы узлов как read (preflight предупреждает); сборки OpenWiki и Graphify выполняются только в обязательной папке - у дополнительных папок кнопки сборки скрыты ("только чтение").

**`sources/` - локальная работа с проектами**: каталог для клонов репозиториев, над которыми ведётся работа (в git не попадает - игнорируется). Кнопка "Клонировать репозиторий": https-ссылка → `git clone` в `sources/<имя>` (job с терминалом; https-only, хосты не из приватных сетей).

Тогглы **OpenWiki**/"Graphify"/"Docs" в каждой строке включают папку в показ документов и списки чтения (`state.workspaces.openwiki` / `.graphify` / `.docs`); убранная из списка папка автоматически снимается с них. Сборка вики и графа всегда идёт в обязательной папке.

## Знание

`/memory` - раздел "Знание": вкладки Docs (документы рабочих папок), OpenWiki, Graphify и **"Память"** (memory-файлы рантаймов). Всё читается с диска, собственных хранилищ нет. Тот же перечень файлов - во вкладке "Память" внутри каждого рантайма (`/runtime/<id>`), в разрезе одного рантайма. В дереве Docs рабочей папки скрываются вложенные рабочие папки (например, `docs/` внутри корня репозитория) - они показываются собственными группами.

### Docs

Все markdown-файлы рабочих папок в глубину (скрытые каталоги, `node_modules`, `.git` пропускаются; лимиты: 500 файлов, глубина 8). Навигация - дерево папок слева, справа - рендер (GFM). Автовыбор: README → AGENTS → первый файл.

### OpenWiki

Сборка вики - внешним [openwiki CLI](https://github.com/langchain-ai/openwiki): `npm install -g openwiki` (Node ≥ 22, LLM-ключ настраивается при первом запуске CLI; ставится и скриптом `bun run setup` - см. AGENTS.md §10). Вики ведётся **на русском языке**: сборка выполняется `openwiki --language ru --init|--update "Веди вики на русском языке."`. Для папок, включённых тогглом в "Рабочих папках", кнопки **Собрать** (`openwiki --init`, если `openwiki/index.md` ещё нет) и **Обновить** (`openwiki --update`). Сборка идёт отвязанным процессом; статус опрашивается раз в 4 с, хвост лога виден в навигации:

- `openwiki/.console-build.json` - pid/режим/время старта (пишет консоль);
- `openwiki/.console-build.log` - вывод сборки;
- `openwiki/.last-update.json` - отметка генерации (пишет сам openwiki).

Прерванная сборка блокирует смену языка: CLI требует завершить её в том же режиме и языке. Консоль распознаёт такое состояние (статус `interrupted` в `.last-update.json` + неснятый `.run.json`) и запускает resume в языке прерванной сборки; после её завершения следующий запуск "Обновить" переходит на русский (деталь плана - `wikiBuildPlan` в `core/memory.ts`).

Второй режим - **"через агент ★"**: сборку ведёт headless-сессия рантайма с установленной интеграцией openwiki (`openwiki integrations install <codex|claude|opencode|cursor> --project` - скилл `SKILL.md` + MCP-сервер `openwiki mcp --host <id>`), а не LLM-провайдер: агент исследует репозиторий и пишет страницы своей моделью через шесть MCP-инструментов жизненного цикла (`openwiki_begin → submit_plan → next_page → submit_page → finish`), OpenWiki владеет состоянием (`.run.json`, claims). Исполнитель - рантайм из задачи "Исполнение команд" (★). Ограничения: агентская сборка ведёт вики git-корня папки запуска (для вложенных рабочих папок - обычный CLI-режим); у cursor нет headless-запуска из консоли, у zcode/kimi - интеграции openwiki. Вывод агента - тот же лог `openwiki/.console-build.log`; задача видна в "Мониторинг → Задачи" со ссылкой на сессию.

Вики хранится в `<папка>/openwiki/` и версионируется вместе с проектом.

### Воркспейсы (мультирепо)

Вики нескольких git-репозиториев объединяются в именованный воркспейс - тогда агентский поиск (`openwiki_search`, локальный FTS по markdown без модельных вызовов) идёт по всем вики-участникам. Реестр - `~/.openwiki/wiki-workspaces.json`; `openwiki link` в CLI - интерактивный TUI, поэтому состав воркспейсов правит консоль по правилам openwiki (минимум две вики; вики - git-репо с собранной `openwiki/.last-update.json`). Блок "Воркспейсы" во вкладке OpenWiki: создание (имя + папки), активный воркспейс по папке (аналог `workspace use/clear`; вики в одном воркспейсе ищется в нём автоматически, при нескольких нужен активный), удаление. На сборку `--init/--update` воркспейсы не влияют - только на области поиска.

### Graphify

Тоггл **Graphify** в "Рабочих папках" включает папку в сборку графа знаний (`state.workspaces.graphify`). Сборка - внешним [graphify CLI](https://github.com/safishamsi/graphify) (`uv tool install graphifyy`, ставится и скриптом `bun run setup`). Граф каждой папки - отдельный воркспейс в хранилище `graphify/<имя>/graphify-out/` (имя - basename папки, при совпадении имён - суффикс из sha256 пути): кнопки **Собрать**/**Обновить** выполняют цепочку `graphify extract <папка> --out graphify/<имя>/ && graphify cluster-only graphify/<имя> --no-label` (extract CLI пишет только `graph.json`; `graph.html` и `GRAPH_REPORT.md` достраивает cluster-only; повторный запуск инкрементален; отвязанный процесс, мета - `graphify-out/.console-build.json`, лог - `.console-build.log`, статус опрашивается раз в 4 с). Собранный граф публикуется автоматически; кнопка **Опубликовать** повторяет публикацию - `graphify-out/graph.html` копируется в `public/graphify/<slug>/index.html`, граф встраивается iframe с того же origin; vis-network грузится с unpkg (просмотр - интернет, сборка локальная). Кнопка **"Граф знаний"** открывает опубликованный граф папки. Кнопка **"Wiki"** собирает wiki из графа: `graphify export wiki --graph graphify/<имя>/graphify-out/graph.json` - статьи markdown в `graphify-out/wiki/` (лог - `.console-wiki.log`). Кнопка **"Статьи wiki"** открывает просмотр статей: дерево слева, markdown справа; `index.md` - точка входа.

Корпус с doc/paper/image-файлами требует LLM-бэкенд: консоль передаёт `--backend` и `--model` из пресета `state.graphifyLlm` (без них CLI не видит ключ Ollama и берёт свою модель по умолчанию) и env-ключ; code-only корпус собирается без ключа. Полная сборка возможна и через headless-рантайм ("через runtime ★" - его окружение может содержать ключ). Управление CLI и per-runtime интеграциями - "Настройки → Инструменты" ([tools.md](tools.md)).

### Визуализатор (граф вики)

Кнопка **"Граф"** у собранной папки встраивает статический визуализатор openwiki прямо во вкладку. Консоль выполняет `openwiki visualize openwiki --export <dir>/openwiki/.visualizer` - чисто локальная и мгновенная генерация (без LLM): 5 файлов (`index.html`, `client.js`, `client-lib.js`, `styles.css`, `graph.json`) публикуются в `apps/console/public/visualizers/<slug>/` и раздаются Next статикой, iframe строит граф с того же origin.

- Если вики обновилась после экспорта - чип "устарел"; кнопка **"Обновить"** перегенерирует граф (мгновенно).
- Сами библиотеки графа (force-graph, marked, DOMPurify, mermaid) грузятся с cdn.jsdelivr.net - для **просмотра** графа нужен интернет; генерация работает офлайн.
- Альтернатива на будущее - запущенный сервер `openwiki visualize --no-open` (loopback, live-reload по SSE): он тоже встраивается в iframe (не ставит X-Frame-Options), но требует управления процессом и портом, поэтому консоль использует статический экспорт.

### Память

Вкладка "Память" раздела "Знание". Memory-файлы, которые пишут сами рантаймы, по рабочим папкам + подгруппа "Глобальные":

| Рантайм | Источники |
|---|---|
| claude | `~/.claude/projects/<slug папки>/memory/` + `~/.claude/CLAUDE.md` |
| codex | `~/.codex/memories/` (sqlite-хранилище консолью не читается) |
| zcode, kimi | файловая память не обнаружена (пустое состояние) |
| cursor | память в SQLite (`state.vscdb`) - не читается |
| opencode | файловая память не обнаружена (инструкции - AGENTS.md) |

Группы навигации: заголовок = имя рантайма, линия вниз на всю ширину; внутри - рабочие папки и "Глобальные".

Безопасность чтения - allowlist корней, realpath, запрет скрытых файлов, потолок 1 МБ (см. [architecture.md](architecture.md), раздел "Безопасность").

## Guard-совместимость

- Консоль читает `.agents/runtime/**`, `.mimosa/`, каталоги данных рантаймов; пишет - только в `.agents/console/` и MCP-конфиги по правилу managed-имён ([mcp.md](mcp.md)). Файлы навыков и конфиги `.agents/runtime` не правит.
- Хук Kimi зеркалирован в `~/.kimi-code/config.toml` с обёрткой (`sh -c 'if [ -f .guardrails/src/cli.ts ]; then …guard…; else exit 0; fi'`). В проекте Harness повреждённый payload или сбой Guardrails блокирует вызов.
- `.gitignore` синхронизирован с политикой: секреты (`.env*`, `*.pem`, `id_rsa`, `secrets/`) вне git; состояние консоли - версионируется.
