# Workflow

## Архитектура

Harness использует LangGraph.js как локальный движок workflow. Отдельный Bun worker читает команды из SQLite, удерживает lease и продолжает запуск после закрытия браузера. LangGraph сохраняет checkpoints через `@langchain/langgraph-checkpoint-sqlite`. Console передаёт live-события через SSE с интервалом 500 мс.

```
Console -> SQLite command -> worker -> LangGraph -> runtime CLI
   ^          |                  |          |
   +---- SSE event ledger -------+----------+
```

Файлы workflow находятся в мастер-каталоге `.agents/skills/master/workflows` (`workflowsRoot` из `.agents/runtime/config.json`); прежний каталог `.agents/workflows` в корне репозитория читается как fallback, каталог `.agents/workflows` рабочей папки - как workspace-каталог. Каталог Harness загружается первым; каталог выбранной рабочей папки перекрывает его по ID. Run сохраняет snapshot: разрешённый YAML, содержимое, metadata и версии использованных ролей и их навыков (включая run-уровневые `/master:` запроса запуска - `input.masterSkills`), модели runtimes, хэши runtime-конфигов, итоговую capability policy и результат разрешения capabilities. Последующие изменения файлов и Settings не меняют созданный run; fork наследует исходный snapshot. Массивы заменяются, объекты объединяются, шаги объединяются по ID, `disabled: true` удаляет шаг. Валидатор отклоняет цикл наследования, неизвестную зависимость, цикл DAG, граф более 100 шагов и несоединённые узлы (узел без входов и выходов при числе узлов больше одного). id workflow уникальны во всей системе: сохранение файла с id, уже занятым другим файлом, отклоняется. Переименование workflow при сохранении создаёт файл с новым именем, удаляет старый и переводит ссылки `extends` во всех workflow на новый id. Переименование шага в редакторе обновляет его id, ссылки `dependsOn`, входы и автоартефакты по всему файлу.

## Шаг и его секции

Один тип узла - шаг. Внутри шага три секции:

| Секция | Поля | Поведение |
|---|---|---|
| `inputControl` (опциональна) | `roles`, `prompt`, `dor`, `maxAttempts` (по умолчанию 10) | Роли проверяют вход по DoR. Провал - задание на доработку поставщику (ролям последней зависимости; у первого шага - пользователю через interrupt с вариантами: контролёр готовит 2-3 готовые формулировки входа, включая рекомендуемую, оператор выбирает вариант, редактирует его или переписывает задание полностью). Каждый возврат расходует попытку; исчерпание останавливает прогон с ошибкой. |
| `execution` (обязательна) | `prompt`, `confirmPlan` | Сначала план по DoD и AC. При `confirmPlan: true` план показывается оператору: закрытие окна без подтверждения ставит прогон на паузу, карточка подтверждения появляется на доске задач. Затем работу выполняют роли шага; инструкции всех ролей и промпт идут в одном промпте. |
| `outputControl` (опциональна) | `roles`, `tests`, `dod`, `ac`, `manualReview`, `maxAttempts` (по умолчанию 10) | Автопроверки: чек-лист тестов и ревью по DoD/AC ролями секции. Пустой список `ac` - AC генерирует движок перед планом из выходных артефактов шага, требований исполнения, описания задачи и DoD (событие `acceptance.criteria`); непустой список - статический override. Провал - задание на доработку исполнителю и повторное исполнение. Упавшие тесты (категория `tests`) попыток не расходуют; отклонение ревью (авто или ручное) расходует. При `manualReview: true` после успешных авто-проверок открывается ручное окно: принять, отклонить с комментарием, отложить (пауза без расхода попыток). Защитный потолок авто-циклов без расхода попыток - `2 × maxAttempts`, затем ручное окно. |

Вердикты контролей - машинный блок ```json `{"verdict":"pass|fail","category":"tests|review","criteria":[{"criterion":"...","status":"pass|fail","note":"..."}],"findings":[],"comments":""}` ``` в конце ответа агента; допустим и сырой JSON-объект без ограждений. Контроль возвращает результат по каждому критерию чеклиста (DoR, DoD, AC); события `input.checked` и `acceptance.review` несут `criteria`, страница прогона показывает прохождение чеклистов в процессе. Если вердикта нет, контроль вызывается заново с фидбеком (начало предыдущего ответа в задании); после двух неудач прогон останавливается. Возвраты (`input.returned`, `acceptance.returned`) несут `failedCriteria`: проваленные критерии входят в файлы `returns/` и в lessons learned. Возврат после проверки сбрасывает отметки "пройден": в чеклистах страницы прогона проваленные критерии остаются проваленными, остальные показываются как не проверенные, чип карточки шага переключается на "возврат".

Прочие поля шага: `roles` (исполнители), `runtime.candidates` (упорядоченный список failover; значения - CLI-рантаймы и провайдеры AI SDK в формате `provider:<id>`, исполняемые в процессе консоли через LangChain-цикл; пустой список наследует `defaults.runtime` workflow), `runtime.tier` и `runtime.effort` (опциональны; наследуются: шаг → defaultTier роли → `standard`/`medium`), `retry.maxAttempts` (попытки failover, по умолчанию 3), `inputs`, `outputs`, `timeoutMs`, `resources.workspace` (`read`/`write`/`worktree`), `dependsOn`, `disabled`, `ui`. На уровне workflow в `defaults.runtime.candidates` задаётся runtime или провайдер по умолчанию: шаги с пустым списком наследуют этот порядок failover, шаги со своим списком переопределяют его; действие Replace у наследующего шага создаёт явный override. В редакторе шага и настройках workflow кандидаты выбираются чипами; чипы перетаскиваются мышью для смены порядка failover.

## Failover runtime

Каждый вызов агента проходит по `runtime.candidates` в порядке списка. Недоступность - рантайм не установлен, ошибка запуска, падение процесса, таймаут или пустой вывод; каждая неудача пишет событие `step.runtime-failed`. Машинный вывод - обёртка вызова: claude вызывается с `--output-format json` (конверт result/usage/cost), codex - с `--json` (JSONL-стрим: текст - последний `item.completed/agent_message`, usage - из `turn.completed`, включая кеш-чтение); рантайм с машинным выводом, вернувший plain-text вместо конверта, уходит в failover. Попытка = полный проход списка; после `retry.maxAttempts` попыток прогон останавливается с ошибкой "рантаймы исчерпаны". Действие Replace переставляет кандидата в начало списка snapshot. Если контроль не вернул машинный вердикт, повтор вызывается с изменённым ключом кеша и фидбеком в задании - повтор после паузы не получает закешированный плохой ответ.

## Инструменты шага (function calling)

Кандидат `provider:<id>` в `runtime.candidates` исполняет секцию в процессе воркера через агентный цикл (`core/agentLoop.ts`): запросы к модели идут через LangChain (`core/langchain/chatModel.ts` - фабрика по kind пресета: openai → ChatOpenAI с базовым URL из записи провайдера, anthropic → ChatAnthropic, gemini → ChatGoogleGenerativeAI), схема инструментов передаётся через `bindTools`, вызовы инструментов исполняет консоль, результат возвращается в контекст следующего раунда как ToolMessage. Модель шага берётся из записи провайдера по tier и замораживается в snapshot.

Встроенные инструменты (`core/agentTools.ts`):

| Инструмент | Аргументы | Ограничения |
|---|---|---|
| `read_file` | `path`, `offset`, `limit` | путь внутри рабочей папки прогона; секретные пути (.env*, *.pem, *.key, id_rsa, .ssh/, secrets/, credentials.json) запрещены |
| `list_dir` | `path`, `depth` (1-3) | та же изоляция пути |
| `run_command` | `command`, `timeout_ms` | Guardrails-проверка (`bun .guardrails/src/cli.ts evaluate`, контракт Bash; сбой блокирует вызов); исполнение `/bin/bash -s`, команда подаётся в stdin |

Вывод инструмента усекается до 16 КБ. Цикл останавливается на ответе без вызовов инструментов; лимит - 10 итераций и `timeoutMs` шага на весь бюджет. Usage попытки - сумма по итерациям. Каждый вызов пишет событие `step.tool-call` (инструмент, аргументы, статус ok/blocked/error, длительность, размер), недоступный при старте MCP-сервер - `step.mcp-unavailable`; вкладка "Инструменты" панели деталей шага показывает их список, транскрипт цикла пишется в `.agents/console/runs/`.

MCP-инструменты ролей шага (поле `mcp` в frontmatter) подключаются MCP-клиентом консоли (`core/mcp/client.ts`) и передаются циклу вместе со встроенными; имена неймспейсятся `mcp__<server>__<tool>`. В диалоге Ассистента (`/api/agent/chat`) те же встроенные инструменты и все включённые MCP-серверы реестра доступны провайдер-исполнителю с лимитом 10 шагов.

## Политика доступности capabilities

Preflight проверяет обязательные skills, MCP и tools каждой роли. Итоговая политика вычисляется в порядке `workflow.defaults.capabilityPolicy` → workspace override → global setting → системное значение `block`. В Settings → Workflow доступны global policy и override рабочих папок; Workflow Studio записывает override `block`/`warn` в YAML или оставляет наследование.

- `block`: отсутствие обязательной capability создаёт ошибку; запуск возвращает HTTP 409 с preflight и совместимыми заменами.
- `warn`: запуск разрешён, warning фиксируется в snapshot, Run Viewer и событии `run.preflight-warning`. Недоступная capability исключается из вызова, а prompt требует использовать fallback роли и записать ограничение в артефакт.

Неизвестная роль, runtime, модель или workspace всегда блокирует запуск независимо от capability policy. Tool доступен, когда он есть в реестре, его CLI обнаружен и интеграция не выключена. MCP проверяется для runtime candidates шага; skill — по manifest и runtime bindings.

## Папка задачи и возвраты

Каждый прогон создаёт папку задачи `.agents/console/tasks/<run-id>/` в корне репозитория консоли (вся информация прогонов консоли - в `.agents/console`, рядом с SQLite и логами): `<step-id>/` с файлами артефактов, `errors/` с файлами ошибок, `returns/` с заданиями на доработку (что не учтено, проваленные критерии, на что обратить внимание), `lessons/` с предложениями lessons learned. SQLite остаётся журналом (события, попытки, usage); файлы - поставкой.

## Lessons learned

Скрытый шаг каждого прогона (не отображается на канве). После завершения графа обходит `errors/` и `returns/` задачи и предлагает обновления ролей и навыков: список {цель, категория auto/manual, diff, причина}. Console показывает модальное окно: вкладки "Автоисправление (выбрано X из Y)" и "Ручное исправление (Z)", чекбоксы выбора; отмеченные правки применяет агент выбранного runtime.

## Предустановленные workflow

В репозитории два предустановленных workflow. `sdlc` - полный цикл разработки: intake, контекст, requirements с входным контролем и ручной приёмкой, гейты (шаги роли approver с `manualReview`), ux/system/technical design, planning с подтверждением плана, исполнение с чек-листом тестов, верификация, release-gate и close. `pdlc` (PDLC Discovery) - короткий продуктовый цикл: discovery, исследование, концепция с ручной приёмкой и финальный planning; шаг planning помечен `execution.producesTasks: true` и поставляет спланированные задачи (с оценкой value/effort из финального ```json-блока) в backlog доски задач.

## Интеграция с AgentsPlane

Задачи из шагов с `execution.producesTasks: true` синхронизируются с AgentsPlane (CLI `agentplane`, плагин "Настройки - Инструменты"; хранилище - `.agentplane/tasks/<id>/` рабочей папки). Id задачи AgentsPlane детерминирован: `YYYYMMDDHHMM-XXXX` (UTC из `createdAt` roadmap-задачи и первые 4 символа `provenance.fingerprint`), поэтому повторный прогон обновляет существующую задачу вместо дублирования. При создании задачи в backlog движок создаёт или обновляет задачу `agentplane task add/update` (owner `HARNESS`, теги `harness`, `backlog`, приоритет: critical - `high`, остальные - как в roadmap). Перевод задачи из workflow в `done` или `archived` на доске roadmap закрывает задачу AgentsPlane (`agentplane task complete`). Все вызовы best-effort: CLI недоступен (exit 3) или упал - событие `plan.tasks-created` несёт счётчики `agentplane` (created/updated/unavailable/error), workflow и roadmap не ломаются. `sdlc:specify`, `sdlc:openspec`, `sdlc:gsd` и `sdlc:bmad` наследуют базовый SDLC и заменяют промпты методологических шагов.

В Console кнопка **"Новый workflow"** создаёт пустой файл, **"Clone / extends"** копирует существующий. Узлы канвы перетаскиваются мышью (позиция сохраняется в поле `ui` шага); при соединении узлов артефакты источника автоматически записываются в `outputs` источника и `inputs` приёмника, при разрыве связи входы очищаются. Кнопка **"Runtime workflow"** в тулбаре открывает редактор runtime по умолчанию (defaults.runtime). В редакторе шага runtime candidates выбираются чипами (CLI-рантаймы и провайдеры AI SDK); чипы перетаскиваются мышью для смены порядка; `dependsOn` заполняется только связями на канве.

Частичный запуск принимает целевой шаг и вычисляет closure зависимостей. Ошибка переводит run в `interrupted`.

## Повторы и детали шага

Правая колонка страницы прогона - панель выбранного шага; отдельной страницы с журналом всего прогона нет. В верхней части панели шага - верхний Segmented: "Данные" (по умолчанию) и секции шага "Входной контроль", "Исполнение", "Выходной контроль" (по наличию секций в шаге). Внутри "Данных" - вложенный Segmented: "Ошибки" (по умолчанию, если ошибки есть), "Лог" (события шага), "Инструменты", "Артефакты", "Агенты", "Статистика". Заголовок панели несёт описание шага, вкладки секций - пояснение назначения секции и задание из workflow. Вкладки секций показывают по шагу: чеклисты DoR (входной контроль) или DoD и AC (выходной контроль) со статусами критериев по последнему вердикту (пройден, провален с пояснением, не проверен; возврат сбрасывает отметки "пройден"), пометки возвратов с критериями, вызвавшими возврат, промты подшагов (с учётом privacy) и статистику подшагов (вызовы, успешные, токены вход/выход/кеш, стоимость, суммарное время). Выходной контроль дополнительно показывает описание AC: статические из workflow или сгенерированные движком (бейдж "сгенерированы движком"). Исполнение показывает циклы плана и исполнения, созданные задачи и вызовы инструментов. Карточки шагов в списке слева несут чипы прогресса DoR и DoD+AC и счётчик возвратов; шаг, ещё не начинавший работу, неактивен (disabled); клик по активной карточке открывает панель шага. Вкладки "Данных": ошибки (первой - ошибка прогона, далее неудачные попытки, события `step.failed`/`step.runtime-failed`/`step.attempt-exhausted` и артефакты `__err-*`), инструменты (вызовы инструментов и MCP у provider-шагов: статус, аргументы, длительность, размер), артефакты шага (выходы), агенты (агенты и субагенты шага) и статистика (токены входа/выхода/кеша и стоимость по попыткам, срез по runtime с моделью, tier и effort шага, счётчики служебных маркеров циклов с человекочитаемыми метками). Состав группы маркеров открывается в отдельном окне по клику на счётчик; содержимое маркера - кликом по имени с учётом privacy. Текстовые артефакты (md, txt, json, yaml и другие текстовые расширения) кликабельны: содержимое открывается в отдельном окне. Промты и содержимое артефактов выдаются только при privacy `full`; при `metadata` показываются размер и контрольная сумма, при `aggregates` - только счётчики. Событие `step.prompt` обезличивается при записи в ledger тем же механизмом, что и остальные события.

Прогон в статусе `completed` не предлагает повтор. Прогон в статусе `failed`/`interrupted`/`cancelled` предлагает два повтора; причина обязательна, как у Skip и Replace:

- **Повтор с начала** (`restart`) - стирает выходы и маркеры исполнения всех шагов (`cachedCall` не вернёт прошлый результат), сбрасывает чекпоинт LangGraph и запускает граф с `START`. Находки ошибок (`__err-*`), возвраты (`__ret-accept-*`, `__ret-input-*`) и предложения lessons learned (шаг `lessons`) остаются в ledger и в папке задачи - они входят в выученные уроки; счётчики файлов продолжают нумерацию, прошлые файлы не перезаписываются.
- **Повтор с последнего удачного шага** (`retry-from-success`) - стирает артефакты только неуспешных шагов; артефакты шагов с последним событием `step.completed` остаются. Исполнение продолжается с чекпоинта; без чекпоинта прогон стартует заново.

Старые файлы ошибок и возвратов в `errors/` и `returns/` при повторах сохраняются: новые записи получают следующие номера.

## Спринты

Спринт исполняет задачи из backlog выбранными workflow. Создание на доске задач (кнопка "Спринт"): шаг 1 - выбор задач с чекбоксами, workflow на каждую задачу и оценки value/effort из планирования; шаг 2 - распределение по параллельным корзинам и ранжирование (порядок внутри корзины = последовательность исполнения).

Создание помечает задачи лейблом `sprint:<id>` и переводит в статус `ready`; далее задачи двигаются по доске: `in-progress` при старте прогона задачи, `done` при завершении, `review` при паузе на подтверждении, `blocked` при ошибке. Записи спринтов хранятся в `.agents/sprints/<id>.yaml`.

Служебный граф спринта (LangGraph, шаги скрыты в списке шагов прогона): `worktrees` (создаёт git worktree на каждую задачу в `.agents/.worktrees/`) → параллельные узлы `bucket-N` (задачи корзины последовательно; каждая задача - отдельный прогон выбранного workflow в своём worktree) → `close` (статус спринта) → `lessons` (ретроспектива: обход ошибок и возвратов задач, предложения по обновлению ролей и навыков - те же вкладки авто/ручных исправлений, что и у обычного прогона).

## Хранение

Git хранит workflow, роли, internal skills и roadmap. Локальная база находится в `.agents/console/workspaces/<workspace-id>/workflows.sqlite`: runs, attempts (role_id, section), checkpoints, event ledger, команды, artifacts, cache и usage receipts. Логи и SQLite не входят в Git.

API: `/api/workflows`, `/api/workflow-runs`, `/api/workflow-runs/:id`, `/api/workflow-runs/:id/events`, `/api/workflow-runs/:id/actions`, `/api/workflow-runs/:id/steps/:stepId`, `/api/roles`, `/api/roadmap`. `POST /api/workflows` поддерживает validate, save и clone через `extends`. `POST /api/workflow-runs` запускает новый run или fork из snapshot. `GET /api/workflow-runs/:id/steps/:stepId` возвращает события, попытки и артефакты шага с учётом privacy прогона. YAML save использует ETag; конфликт возвращает HTTP 409 и текущий текст файла, редактор показывает base, current и draft рядом.

Доска задач находится на `/tasks`: карточка = прогон; колонки "В работе", "Требует подтверждения", "Выполнены", "Остановлены". Roadmap (`/`) остаётся отдельной kanban-доской со статусами `inbox` - `archived`.
