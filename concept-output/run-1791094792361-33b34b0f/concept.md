## 2. Problem statement и позиционирование

### Проблема

Когда входной или выходной контроль возвращает ответ без пригодного машинного вердикта, оператор не получает достоверного результата проверки критериев. Прогон останавливается, и оператор должен определить причину и выбрать способ продолжения.

### Позиционирование

**«Устойчивый контрольный вердикт» — функция надёжности контроля Harness для операторов и авторов многошаговых workflow.** Она проверяет единый контракт ответа, допускает одну попытку исправления формата и показывает отдельную причину остановки, если получить валидный результат не удалось.

### Value proposition

| Польза | Механизм | Измерение |
|---|---|---|
| Меньше протокольных остановок | Проверка контракта и одна repair-попытка | Доля терминальных протокольных остановок |
| Меньше ручных повторов | Автоматическое восстановление формата | Медиана действий на затронутый прогон |
| Понятная причина и действие | Раздельные состояния протокола, транспорта и предметного отказа | Полнота диагностики; пользовательские наблюдения |
| Сохранение надёжности контроля | Продолжение только по валидному, согласованному результату | Ложные принятия |

**Гипотеза:** функция снизит протокольные остановки и ручные действия. Рост completion rate проверяется отдельно: функция не устраняет все причины незавершения.

## 3. Минимальный scope

Все положения ниже — предлагаемый контракт первой поставки.

| ID | Требование |
|---|---|
| FR-01 | Входной и выходной контроль используют единый контракт: `verdict`, `category`, `criteria`, `findings`, `comments`. Проверяются обязательность, допустимые значения, покрытие ожидаемых критериев и согласованность результата. |
| FR-02 | Ответы runtime нормализуются перед общей проверкой. Legacy-формат не получает исключений из правил валидации. |
| FR-03 | При нарушении формата допускается не более одной идемпотентной repair-попытки на логический контроль. Она не расходует предметную попытку контроля. |
| FR-04 | После неуспешного исправления фиксируется `control_protocol_error`. Транспортный сбой и валидный предметный `fail` классифицируются отдельно. |
| FR-05 | Диагностика содержит причину, шаг и секцию, runtime, попытку, результат восстановления и доступное следующее действие. |
| FR-06 | Повторная доставка не создаёт повторного перехода, возврата, repair или учитываемого результата. Поздний ответ после отмены не продолжает прогон. |
| FR-07 | При privacy `metadata` телеметрия не сохраняет полный ответ, prompt или свободный текст findings. |
| FR-08 | Ручное принятие оформляется отдельным авторизованным решением с причиной и записью в ledger. До утверждения прав и privacy-политики оно недоступно. Автоматический `pass` из невалидного ответа не создаётся. |
| FR-09 | Поставка управляется feature flag. Порядок отключения, обработка текущих контролей и владелец операции документируются до пилота. |

### Правила границы

- Repair исправляет представление ответа. Изменение критериев, скрытое преобразование `fail` в `pass` и принятие конфликтующих JSON-блоков недопустимы.
- Валидный `fail` сохраняет существующие правила возврата и бюджета попыток. В частности, категория `tests` не должна начать расходовать предметные попытки.
- Транспортные повторы ограничиваются отдельной политикой и не увеличивают разрешённое число repair-попыток.
- Авторизованный ручной повтор создаёт новую проверку со ссылкой на предыдущую. Повторная доставка команды новую проверку не создаёт. Техническое представление идентичности контроля определяет Technical lead.
- Список runtime первой поставки утверждается после проверки совместимости. Перечень кандидатов в workflow не является подтверждением совместимости.

**Вне scope:** изменение пользовательского запроса и DoR/DoD/AC, рейтинг runtime, межорганизационная аналитика, новый аналитический dashboard, миграция исторических событий и полный ремонт worker lifecycle. Защита текущего контроля после отмены обязательна.

## 4. UX-контракт

### Основной путь

```text
Запуск контроля
  -> получение и проверка ответа
     -> валидный pass -> продолжение один раз
     -> валидный fail -> предметный возврат по существующим правилам
     -> ошибка формата -> одна repair-попытка
        -> валидный ответ -> обработка pass или fail
        -> невалидный ответ -> ошибка протокола и диагностика

Транспортный сбой -> отдельная политика восстановления
Отмена -> запрет дальнейших переходов текущего контроля
```

Оператор видит состояние в существующей панели шага и соответствующей секции контроля. История восстановления доступна без обязательного ручного действия.

### Проверяемые пользовательские сценарии (F-01)

Сценарии S-01–S-04 выполняются отдельно для входного и выходного контроля каждого runtime поставки. Общие условия: активный, не отменённый PDLC-run, известные версии схемы и workflow, зафиксированные ожидаемые критерии, feature flag включён, детерминированные ответы тестового runtime. Проверяющий сопоставляет состояние панели с журналом переходов по одному `control_id`. Это проект проверок, а не отчёт об испытаниях.

| ID / сценарий | Роль | Исходные условия | Действия участника и системы | Наблюдаемый результат |
|---|---|---|---|---|
| S-01. Валидный вердикт | Оператор | Контроль готов к запуску; ответ содержит единственный валидный `pass`, все ожидаемые критерии покрыты и выполнены | Оператор запускает шаг и открывает соответствующую секцию; Harness получает и проверяет ответ | «Контроль пройден»; следующий допустимый этап выполняется один раз; repair=0; предметного возврата нет |
| S-02. Успешное исправление | Оператор | Первый ответ имеет дефект формата; второй ответ валиден и согласован с неизменными критериями; проверить варианты `pass` и `fail` | Оператор запускает шаг и наблюдает секцию без ручного повтора; Harness показывает восстановление и делает одну repair-попытку | Отметка о восстановлении; repair=1. При `pass` — один переход, при `fail` — один предметный возврат по существующим правилам, без продолжения. Критерии и смысл отказа не изменены |
| S-03. Неуспешное исправление | Оператор | Первый и второй ответы невалидны; транспорт работает; право ручного повтора предоставлено | Оператор запускает шаг, после остановки открывает диагностику и выбирает «Повторить контроль»; Harness завершает одну repair-попытку, затем обрабатывает ручную команду | До нажатия: отдельный `control_protocol_error`, причина, шаг, секция, runtime, попытка, результат repair и действие; нет автоматического продолжения или предметного возврата, DoR/DoD/AC не помечены проваленными. | S-04. Валидный отказ по критериям | Автор workflow | Контроль готов; ответ валиден, содержит `fail` и известные невыполненные критерии; версия и бюджет возврата зафиксированы | Автор запускает проверку подготовленного шага, открывает результат и сверяет нарушенные критерии; Harness применяет существующий маршрут возврата | «Критерии не выполнены», доступные сведения о критериях и адресате доработки; один предметный возврат, repair=0, автоматического продолжения нет. В варианте `category=tests` предметный бюджет не расходуется |
| S-05. Отмена | Оператор | Контроль или repair выполняется, ответ задержан | Оператор отменяет run; проверяющий доставляет задержанный ответ | Run остаётся отменённым; нет перехода, возврата или новой repair-попытки |
| S-06. Повторная обработка | Оператор | Результат уже применён | Оператор открывает историю; проверяющий повторно доставляет тот же результат и команду | Состояние сохраняется; нет повторного перехода, возврата, repair и учёта результата |
| S-07. Диагностика при metadata | Оператор | Возникла ошибка протокола; содержимое ответа недоступно по политике | Оператор открывает диагностику в панели контроля | Видны разрешённые причина, контекст и действие; prompt, полный ответ и свободный текст findings не раскрываются |

Для S-03 тест фиксирует состояние до ручного повтора отдельно от нового контроля. Повторная доставка результата не равна авторизованной новой проверке. Основной путь S-01, отказ S-03/S-04 и границы S-05/S-06 проверяются подсчётом переходов, а не только текстом статуса.

### State matrix

| Сценарий | Наблюдаемое состояние | Действие и результат |
|---|---|---|
| Контроль ещё не выполнялся | «Контроль не выполнен»; критерии не проверены | Отсутствие результата не отображается как успех |
| Валидный `pass` | «Контроль пройден» | Следующая секция запускается один раз |
| Валидный `fail` | «Критерии не выполнены» | Автор видит нарушенные критерии; выполняется предметный возврат |
| Первый ответ невалиден | «Исправляется формат ответа» | Выполняется одна repair-попытка; критерии не отмечаются пройденными |
| Исправление успешно | Итоговый `pass` или `fail`; отметка о восстановлении | Применяется исправленный результат один раз |
| Исправление неуспешно | «Не удалось получить результат контроля» | Причина и действие «Повторить контроль»; автоматического возврата по критериям нет |
| Транспортная ошибка | «Не удалось получить ответ runtime» | Отдельная диагностика и ограниченное восстановление |
| Отмена во время контроля или repair | «Прогон отменён» | Поздний ответ не запускает следующий шаг или новую repair-попытку |
| Повторная доставка | Состояние сохраняется | Повторные side effects и учёт результата отсутствуют |
| Нет доступа к содержимому | «Содержимое недоступно при текущем режиме приватности» | Остаётся разрешённая диагностика; пустое поле не трактуется как отсутствие ошибки |

**Пограничные случаи:** отсутствующий критерий, неизвестный статус, конфликтующие блоки, `pass` при проваленном критерии и неизвестная версия схемы не допускают автоматическое продолжение.

### Ручное принятие

Оператор с соответствующим правом видит предупреждение: **«Результат контроля не установлен. Продолжение будет записано как ручное решение».**

До реализации необходимо определить право, допустимые причины и формат аудита. При `metadata` предлагается хранить код причины; хранение свободного комментария требует отдельного решения Security reviewer.

### Accessibility и требования к макетам

- Причина и следующее действие выражены текстом; цвет используется дополнительно.
- Действия доступны с клавиатуры, фокус видим.
- Изменение статуса доступно вспомогательной технологии без неожиданного переноса фокуса.
- Повтор недоступен во время уже выполняющегося запроса.
- Следующий дизайн-артефакт должен показать как минимум восстановление, неисправимую ошибку, предметный отказ и отмену.

**Покрытие:** подготовлены текстовые flows, самостоятельные сценарии и state matrix. В предыдущей редакции зафиксированы недоступность OpenDesign Cloud и отсутствие Figma MCP; в этой доработке дизайн-провайдеры не вызывались. Их доступность сейчас не подтверждена. Визуальный прототип, клавиатурная проверка и проверка вспомогательной технологией не выполнены.

## 5. Метрики и success criteria

Обозначения:

- **N** — число включённых терминальных прогонов пилота.
- **A** — подмножество этих прогонов хотя бы с одним невалидным вердиктом.
- **C** — число независимо проверенных логических контролей.

Все пороги ниже требуют утверждения.

| Метрика | Определение, единица и расчёт | Выборка и источник | Baseline | Предлагаемый критерий |
|---|---|---|---|---|
| **Протокольные терминальные остановки** | Процент: `100 × runs с непосредственной терминальной причиной protocol error / N` | Все N; финальное состояние run и связанное событие причины. История: `eligible-runs.csv` + `root-cause-review.md` | **3/5 = 60%** | **≤10%, N≥30** |
| Встречаемость невалидного вердикта | Процент: `100 × число runs в A / N`, включая успешно исправленные ответы | Все N; события валидации. История: `problem-aggregates.csv` | 4/5 = 80% | Диагностическая метрика, без порога успеха |
| **Ложные принятия** | Число уникальных контролей с автоматическим продолжением по невалидному, неоднозначному либо противоречащему независимому эталону результату; дубль учитывается один раз | C контролей; `audit-controls.csv`, `oracle.csv` и `transitions.csv` по BL-01 ниже | Исторически не восстановим; начальное измерение B0 по BL-01 ещё не выполнено | **0 при C≥30**; полевой и синтетический аудит публикуются отдельно |
| Completion rate | Процент: `100 × completed / N` | Все N; экспорт состояний runs | 0/5 = 0% | Вторичная цель ≥20%, рост ≥20 п. п. |
| Ручные действия: исторический proxy | Медиана уникальных `run.action` на run из A; действий/прогон | Все A, включая runs с нулём действий; event ledger. История: `event-metadata.csv` + `problem-aggregates.csv` | 3; A=4, всего 18 действий | Вторичная цель ≤1; причинная атрибуция ограничена |
| Полнота диагностики | Процент: `100 × D_complete / D`; один завершённый протокольной ошибкой логический контроль — одна единица | Все D ошибок в измеряемом наборе; `diagnostic-audit.csv`, export events и снимки панели/дерева доступности по BL-02 | Исторически не восстановим; начальное измерение B0 по BL-02 ещё не выполнено | 100%; полевой и синтетический результаты отдельно |
| Действия, связанные с протокольной причиной | Медиана уникальных действий с `cause_event_id` на затронутый run; действий/прогон, включая нулевые значения | Затронутые runs наблюдательной когорты; связанный экспорт действий и событий причин | Отсутствует; Data owner собирает на B0 с наблюдательной телеметрией до включения repair | Диагностический показатель; порог отдельно утверждает approver после baseline |

### Начальное измерение отсутствующих baseline (F-02)

**Почему историю нельзя восстановить.** В research-export сохранены metadata без полных ответов, независимой разметки ожидаемого результата, версии engine каждого run и снимков показанной диагностики. `event-metadata.csv` не содержит полного набора полей FR-05. Поэтому отсутствие поля в экспорте не доказывает его отсутствие в интерфейсе, а отсутствие зарегистрированного ложного принятия не доказывает ноль ошибок. Ни 0%, ни 100% историческим метрикам не присваиваются.

**Версия и единый источник сравнения.** До реализации Workflow maintainer фиксирует B0 — конкретный commit SHA последней выбранной версии без новой функции, версии runtime, workflow, правила контроля, privacy и feature flag=off. Data owner записывает их в `measurement-manifest.json` вместе с cutoff, идентификаторами набора и SHA-256 всех входов. Значение B0 пока не выбрано: назначать текущий HEAD версией исторических пяти runs нельзя. Для B1 фиксируется commit поставки, те же входы и эталон, feature flag=on. Если B0 недоступна или эталон изменён, сравнение помечается несопоставимым; B1 служит только начальной точкой нового ряда, а не доказательством улучшения.

Названия файлов ниже — **контракт будущей выгрузки**, этих измерений сейчас нет. Набор хранится в отдельном каталоге `baseline-b0/`, результат B1 — в `pilot-b1/` внутри evidence пилота. Manifest содержит разрешённые идентификаторы и хэши, без рабочих prompt и ответов. Исходные ответы в наборе синтетические; сбор полевых данных требует утверждённой privacy-политики.

#### BL-01. Ложные принятия

- **Владелец:** QA создаёт и выполняет набор; независимый verifier утверждает эталон до запуска; Data owner связывает события; Product analyst рассчитывает показатель.
- **Выборка:** минимум 30 отдельных логических контролей на B0; оба вида контроля и каждый runtime поставки. По каждой паре runtime × секция покрываются валидные `pass`/`fail`, отсутствие критериев, неизвестный статус критерия, конфликтующие блоки, `pass` при невыполненном критерии, неизвестная версия схемы, неисправимый JSON, отмена и повторная доставка. Объём увеличивается, если 30 недостаточно для покрытия. Дубликаты одного контроля C не увеличивают.
- **Источники:** синтетические входы и ожидаемые критерии в версионированном наборе; `oracle.csv` (`case_id`, допустимый результат, допустимость перехода, код основания, reviewer); `transitions.csv` (версии, `run_id`, `control_id`, `event_id`, вид и время перехода, признак автоматического/ручного решения); `audit-controls.csv` (связь case/control, итоговый ответ по ID синтетического входа, независимая оценка, факт автоматического продолжения).
- **Процедура:** зафиксировать эталон без использования результата parser как истины; подать ответы через реальный путь нормализации и контроля B0; дождаться итогового состояния и сохранить переходы. Для каждого контроля сопоставить фактическое автоматическое продолжение с эталоном. Ручной override классифицировать отдельно. Пропавшая связь или незавершённый контроль означает неполное измерение, а не отсутствие ложного принятия.
- **Расчёт и сравнение:** число уникальных `control_id` с ложным принятием; рядом публикуются C, список case_id и покрытие. Повторить тот же набор на B1. Синтетический baseline и B1 сравниваются между собой; полевой аудит C≥30 публикуется отдельно и не подменяется синтетическим набором. При privacy=metadata неразрешённое сохранение ответов не допускается: QA проверяет полевые результаты в разрешённой сессии и сохраняет структурированную оценку; если аудит невозможен, порог считается непроверенным.
- **Имеющееся evidence:** research `control-verdict-fixture.test.ts` проверяет только parser. CV-03/CV-04/CV-05 принимают `pass` с дефектами, CV-07 принимает невалидный `fail`. Эти четыре случая не равны четырём ложным автоматическим продолжениям. Fixture используется как основа набора, но не заменяет BL-01.

#### BL-02. Полнота диагностики

- **Владелец:** UX designer задаёт проверку полей и следующего действия; QA снимает состояния; Data owner связывает данные; Product analyst рассчитывает показатель.
- **Выборка:** все контроли с окончательной протокольной ошибкой в синтетическом наборе B0, отдельно от успешно восстановленных. Минимум два случая на runtime × секция: отсутствие пригодного вердикта и невалидный JSON после исчерпания текущих повторов. Если основной набор их не обеспечивает, дополнить его до запуска B0 и зафиксировать новую версию. Для B1 использовать те же входные последовательности. В поле учитывать все такие ошибки во включённых N; если D=0, результат «не применимо».
- **Источники:** экспорт событий контрольного пути B0/B1 и текст/снимок существующей панели шага и её дерева доступности на том же build. `diagnostic-audit.csv` связывает `case_id`, `control_id`, причину окончания, ID событий, ссылку на снимок и отдельный результат проверки каждого обязательного поля. Исторический CSV без снимка интерфейса недостаточен.
- **Полный набор полей:** безопасная причина ошибки, шаг, секция, runtime, номер попытки, результат восстановления и доступное следующее действие. Поле считается заполненным, если значение корректно, понятно и доступно оператору в панели без раскрытия содержимого. Значение только в служебном логе недостаточно. Следующее действие проверяется по состоянию и правам. На B0 допустим явный текст «автоматическое исправление формата недоступно»; отсутствие такого сообщения считается пропуском поля результата восстановления.
- **Процедура:** вызвать каждый отказ на B0, открыть панель оператором с заданными правами, сопоставить поля с событием и фактическим состоянием, записать по каждому полю `present/correct/available`. D_complete включает только строки, где все семь полей прошли проверку; D включает все вызванные окончательные протокольные ошибки, даже если B0 не имеет отдельного кода `control_protocol_error` — их классифицируют по известному синтетическому входу и фактическому исходу. Отсутствие диагностики даёт неполную строку, а не исключение из D.
- **Расчёт и сравнение:** публиковать D_complete, D и процент по версии и runtime/секции; при расхождении исходов B0/B1 показывать изменение состава D. Для прямой проверки качества полей использовать парные случаи с протокольной остановкой на обеих версиях. Полнота не доказывает понятность: OBS-H01–OBS-H05 остаются отдельной проверкой.

**Условие до начала пилота:** B0 выбран и сохранён, оба измерения выполнены, отчёт содержит числители, знаменатели, ссылки на исходные строки и checksum; либо approver явно принимает отсутствие сопоставимого baseline с запретом утверждать улучшение этих метрик. Такой выбор не отменяет абсолютные требования B1: ноль ложных принятий и полная диагностика.

**Другие отсутствующие baseline:** причинно связанные действия измеряет Data owner на отдельной последовательной когорте ≥30 терминальных PDLC с B0 и наблюдательной связью `cause_event_id`; ручная атрибуция допустима только как отдельно размеченный источник. Если наблюдательная инструментализация B0 невозможна, первое измерение B1 становится исходной точкой без исторического сравнения. Полную длительность контроля QA измеряет на том же парном наборе B0/B1 от начала контроля до итогового результата, включая повторы; полевое время хранится отдельно. До решения approver пороги для этих двух диагностических показателей не назначены.

Если A пусто, медиана — **«не применимо»**. Если ошибок протокола нет, полевая полнота диагностики не вычисляется; проверка на fixtures остаётся обязательной.

**Отличие от research:** порог 10% применяется к терминальным остановкам. Частота первичных невалидных ответов может оставаться высокой при успешном восстановлении. Историческую медиану всех действий нельзя переносить на новый причинно связанный показатель.

### Дополнительные ограничения качества

- Ни одного автоматического продолжения после отмены или повторного перехода при дублировании.
- Ни одной обнаруженной утечки контрольного содержимого в metadata-хранилища.
- Время логического контроля измеряется целиком, включая repair. Baseline и допустимое увеличение пока отсутствуют; решение принимают Technical lead и product approver.
- Исследовательский p95 отдельной входной попытки нельзя подменять длительностью всего контроля.

Ноль обнаруженных ложных принятий в 30 проверках — ограниченный результат проверки, а не доказательство нулевого риска.

## 6. Протокол пилота

1. **До старта** назначить approver, утвердить runtime, privacy, сроки набора, пороги и правила остановки. Зафиксировать версию функции, схемы, workflow и feature flag; выполнить BL-01/BL-02 или записать допустимое решение об отсутствии сравнения согласно §5.
2. Включать последовательные PDLC-прогоны сегмента с заполненным `started_at` и статусом `completed`, `cancelled`, `interrupted` или `failed`.
3. Набрать **не менее 30 терминальных прогонов**. Не исключать отмены, transport failures или предметные отказы из-за неблагоприятного результата.
4. Исключить текущий исследовательский run, другие workflow, дубликаты и заранее помеченные синтетические проверки. Незавершённые runs показать отдельно с возрастом ожидания.
5. На установленный момент среза учитывать каждый `run_id` один раз. Resume обновляет тот же run; новый ID считается отдельно. Изменение версии создаёт отдельную когорту.
6. Независимо проверить **не менее 30 логических контролей**, покрыв обе секции и все runtime первой поставки. При необходимости увеличить объём для полного покрытия.
7. Включить валидные `pass`/`fail`, исправимые и неисправимые ответы, неоднозначность, transport failure, дубликаты и отмену. Синтетические проверки не входят в знаменатель полевых PDLC.
8. Сохранить обезличенную выгрузку, inclusion/exclusion manifest, дедупликацию, checksum и расчётный скрипт. Публиковать числители, знаменатели и интервал неопределённости основной доли.

**Обязательный результат:** протокольные остановки ≤10% и ноль ложных принятий. При N=30 допускается максимум три протокольные остановки.

Недобор N или C означает недостаточность данных, а не успех. Прогоны, завершившиеся после начала исполнения до первого контроля, остаются в N; аудит C и диагностика D используют свои знаменатели.

**Управление поставкой:** Workflow maintainer при стоп-условии останавливает набор и новые контроли, отключает feature flag для новых запусков, сохраняет разрешённые evidence и проверяет отсутствие продолжения отменённых контролей. Technical lead до пилота документирует судьбу уже выполняющихся контролей и привязку их версии. Автоматическая повторная обработка незавершённых контролей старым parser не допускается. Возобновление после разбора требует отдельного решения владельца пилота.

**Предлагаемые стоп-условия:** ложное принятие, утечка содержимого, продолжение после отмены или повторный переход. Workflow maintainer приостанавливает пилот; QA и Security reviewer проверяют причину. Возврат к прежнему parser сам по себе не доказывает безопасность и требует отдельного решения.

print("N, A, terminal_protocol, completed, actions_A, median:", result)
print("SHA256:", len(checks), "/", len(checks), "post_terminal:", late)
