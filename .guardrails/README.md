# Guardrails

Каталог содержит исполняемую политику Harness и доказательства её применения. Источник правил — `src/rules.ts`. Команда `generate` создаёт отдельную карточку каждого правила и сводные отчёты в `generated/`.

## Контракт

```text
stdin:  {"tool_name":"Bash","tool_input":{"command":"…"}}
exit 0: разрешено; предупреждение выводится в stderr
exit 2: заблокировано; stderr содержит rule id, причину и исправление
```

Повреждённый payload блокируется. В журнале `audit/events.jsonl` сохраняются время, интеграция, решение, rule id и SHA-256 payload. Исходные аргументы и содержимое файлов не сохраняются. Журнал локальный и исключён из Git.

## Команды

| Команда | Назначение |
|---|---|
| `bun .guardrails/src/cli.ts evaluate` | Проверить payload из stdin |
| `bun .guardrails/src/cli.ts list` | Вывести правила |
| `bun .guardrails/src/cli.ts explain <id>` | Показать правило и тестовые кейсы |
| `bun .guardrails/src/cli.ts where <id>` | Показать точки применения |
| `bun .guardrails/src/cli.ts audit --json` | Создать актуальный снимок аудита |
| `bun .guardrails/src/cli.ts generate` | Обновить карточки и отчёты |
| `bun .guardrails/src/cli.ts prompt` | Проверить промпт из stdin: {prompt, session_id, surface} |
| `bun .guardrails/src/cli.ts scan-diff` | Скан добавленных строк diff из stdin |
| `bun .guardrails/src/fprcheck.ts` | Замер ложных срабатываний на корпусе чистых промптов (25 шт., детерминированно) |
| `bun .guardrails/src/decisions.ts` | Статистика решений за период: эффекты, правила, точки, задержка (p95) |
| `bun .guardrails/src/adapters.ts check` | Сверка точек подключения по реестру рантаймов |
| `bun .guardrails/src/adapters.ts render <id>` | Фрагменты конфигурации для рантайма; новые рантаймы добавляются записью в `src/runtimeAdapters.ts` |
| `bun .guardrails/src/scanhistory.ts` | Разовая проверка истории Git: `--range <expr>`, `--limit N`, `--show-values` (только ПДн), `--fail-on-secrets` |
| `bun run asr -- --provider <id>` | ASR-прогон корпуса на живой модели: без защиты и с защитой, вердикт судьи; exit 2 при превышении порога |
| `bun .guardrails/src/cli.ts check` | Проверить каталог, wiring и отчёты |
| `bun test .guardrails/tests` | Выполнить тесты всех правил и CLI |

## Контентный сканер и защита LLM-трафика

Кроме проверок tool-вызовов, движок содержит контентный слой (`src/content/`) и слой LLM-обёрток (`src/llm/`). Сканер находит классы данных по поверхностям: `write` (записываемое содержимое файлов), `prompt` (промпты), `tool-output` (выводы инструментов и документы), `llm-io` (тексты, идущие в модель и возвращающиеся из неё). Классы: инъекции инструкций (включая декодированные варианты base64, hex, rot13 и NFKC), секреты и ключи провайдеров, персональные данные (почта, телефоны, карты с проверкой Луна, ИНН с контрольной суммой, СНИЛС, паспорт, SSN), присвоения секретов в коде и маркеры конфиденциальности. Находка не содержит совпавшего текста - только id класса, число вхождений и путь к полю.

| Модуль | Назначение |
|---|---|
| `src/content/patterns.ts` | Реестр паттернов с поверхностями и валидаторами |
| `src/content/scan.ts` | Скан текста и вложенных структур, декод-варианты |
| `src/content/redact.ts` | Замена данных на плейсхолдеры `[REDACTED:<label>]` |
| `src/content/probes.ts` | Счётчик многоходовых PII-зондов по сессии (порог 3) |
| `src/content/catalog.ts` | Каталог контентных правил для слияния с `src/rules.ts` |
| `src/llm/session.ts` | Реестр значений сессии и закодированных вариантов |
| `src/llm/guard.ts` | Точки `guardPrompt` / `guardOutput` |
| `src/llm/wrappers.ts` | `withLlmGuard` (LangChain и совместимые), узел LangGraph |
| `src/llm/schema.ts` | Принудительная схема и вредоносные классы в выводе |

Входная точка `src/posttooluse.ts` подключается хуками PostToolUse (Claude Code, ZCode): сканирует вывод инструмента до передачи в модель, инъекция даёт exit 2 с указанием модели обработать вывод как данные; вывод инструментов, обращённых к артефактам Guardrails, не сканируется (фильтр в `src/content/selfscan.ts`). Матрица поддержки по рантаймам - в `docs/runtimes.md`.

Реестр сессии наполняется идентичностью пользователя из git config (имя, почта) при сборке моделей консоли - значения редактируются во всех промптах и ответах. ASR-прогон (`apps/console/scripts/asr.ts`) измеряет attack success rate на живой модели до и после защиты: подставная личность в системном промпте, детерминированные индикаторы утечки и JSON-вердикт судьи; отчёт пишется в `.agents/.tmp/asr/report.json`.

Консоль оборачивает фабрику моделей (`apps/console/src/core/langchain/chatModel.ts`): инъекция в промпте отклоняется ошибкой `GuardBlockedError`, персональные данные и секреты заменяются плейсхолдерами в промпте и в ответе, значения реестра сессии редактируются вместе с base64, hex, rot13, посимвольными и unicode-вариантами. Обёртка не зависит от библиотеки: прототип модели и поток чанков сохраняются, `bindTools` возвращает снова обёрнутую модель.

Подключение защиты Git и промптов: `.husky/pre-commit` сканирует staged diff (секреты блокируют коммит, персональные данные дают предупреждение); CI сканирует добавленные строки diff pull request; `verify-security` сканирует рабочий diff. Из скана исключены самодиагностирующие артефакты Guardrails (`.guardrails/rules`, `.guardrails/generated`, `.guardrails/tests`, `.guardrails/src/content`) - карточки правил, fixtures корпуса и каталог паттернов легитимно содержат примеры образцов; хуки UserPromptSubmit в Claude Code и ZCode считают PII-зонды и предупреждают об инъекциях в промптах и работают fail-open - блокировка на пороге зондов включается снятием `|| exit 0` в команде хука. Промпт-скан различает поверхность: `surface=agent` блокирует инъекции, `surface=user` только предупреждает.

Регрессия защищается корпусом атак `tests/fixtures/attacks.json` (классы прямых и непрямых инъекций, jailbreak, PII-зонды, редактирование, аргументы вызовов инструментов) и тестами `bun test .guardrails/tests`.

## Интерфейс аудитора

Вкладка «Настройки → Guardrails» показывает понятное название каждого правила, контрольной проверки и точки применения. Стабильный ID отображается второй строкой и используется для поиска, отчётов и автоматизации.

Нажмите элемент, чтобы открыть расшифровку:

- правило: назначение, защищаемые ресурсы, действие, порядок исправления, опасный, допустимый и граничный тестовые сценарии;
- контрольная проверка: цель, предотвращаемая ошибка и проверяемое доказательство;
- точка применения: назначение, защищаемые ресурсы, файл подключения, текущее состояние и поведение при сбое.

Интерфейс читает тот же снимок аудита, который возвращает `bun .guardrails/src/cli.ts audit --json`. Поэтому названия и пояснения входят в проверяемый контракт, а не хранятся отдельно в UI.

## Структура

| Путь | Содержимое |
|---|---|
| `policy.json`, `schemas/` | Версия политики и формальные контракты |
| `src/` | Bun-движок, каталог, аудит и генератор |
| `src/content/` | Контентный сканер: паттерны, скан, редактирование, зонды, каталог правил |
| `src/llm/` | Защита LLM-трафика: реестр сессии, guard, обёртки моделей, схема вывода |
| `rules/<id>/` | Метаданные, кейсы и описание каждого правила |
| `integrations/registry.json` | Реестр `code`, `runtime:hook`, Husky, verification и CI |
| `tests/` | Динамическое покрытие hit/pass/edge, CLI и wiring |
| `threat-model/` | Границы защиты и остаточные риски |
| `exceptions/` | Формат и журнал временных исключений |
| `generated/` | Детерминированные документы для ревью diff |
| `audit/` | Локальные события решений без исходных данных |

## Добавление правила

1. Добавьте правило и минимум три кейса в `src/rules.ts`: `hit`, `pass`, `edge`.
2. Укажите стабильный ID, угрозу, действие, критичность, failure mode и исправление.
3. Выполните `bun .guardrails/src/cli.ts generate`.
4. Выполните `bun test .guardrails/tests` и `bun .guardrails/src/cli.ts check`.

Изменение точки применения требует обновить `src/integrations.ts`. Проверка wiring завершится ошибкой, если заявленный файл или маркер отсутствует.
